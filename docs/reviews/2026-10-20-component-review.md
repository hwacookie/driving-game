## 2. Performance & Code Quality Issues

> **The Impact column below is inferred from code shape, not measured** — it
> ranks call sites by how often they run and what they allocate. The measured
> baseline is in **§4**; where the two disagree, §4 wins.

- [ ] **`MapRenderer._Process`** `MapRenderer.cs:1287-1299`
  - **Type:** Hot-Path Allocation (render loop)
  - **Finding:** In embedded mode every rendered frame runs `IngestState(JsonSerializer.SerializeToUtf8Bytes(_simHost.Engine.StateSnapshot()), "embedded /state")` — the full state dictionary is copied, serialised to a fresh byte array, and re-parsed as JSON, then walked key-by-key. The comment admits it: "serialize + parse keeps state application single-sourced; the cost is negligible vs an HTTP round trip". That comparison is wrong: there is no HTTP round trip in this branch, so the JSON round-trip is pure overhead — hundreds of allocations per frame, and it is the reason the embedded mode still needs the interpolation buffer.
  - **Impact:** **High**
  - **Recommendation:** Give `SimEngine` a typed snapshot record (`CarState` fields, not `Dictionary<string, object?>`) and have the embedded branch feed `IngestState` from that record. Keep the JSON path only for the HTTP branch, so "single-sourced" means one *consumer*, not one *wire format*.

- [ ] **`SimEngine.StateSnapshot`** `DrivingGame.Sim/SimEngine.cs:173`
  - **Type:** Hot-Path Allocation
  - **Finding:** `lock (_stateLock) return new Dictionary<string, object?>(GameState);` — a full copy of a ~40-key dictionary whose values are themselves freshly built dictionaries and lists, taken under a lock. Called once per rendered frame (embedded), once per `GET /state`, and once per 50 ms inside the `/wait` loop (`GameApi.cs:386`).
  - **Impact:** **High**
  - **Recommendation:** Build the payload once per tick into an immutable snapshot object and hand out the reference (no copy). If a dict must stay for the REST contract, build it lazily only on the HTTP endpoints.

- [ ] **`SimEngine.UpdateState`** `DrivingGame.Sim/SimEngine.cs:1046-1245`
  - **Type:** Hot-Path Allocation / Un-idiomatic C#
  - **Finding:** Per frame, per car, a fresh `Dictionary<string, object?>` with ~30 keys is built, plus `LgStatsPayload`, `FlagsPayload`, and `ObstacleGeometry.PlayerBodyCorners(c).Select(p => new[]{p.X,p.Y}).ToList()` (`:1096`, `:1190`) — four heap arrays plus a list per car per frame. Then the top-level payload is a second ~40-key dict, and the two payload shapes (car present / no car) are written out separately with ~15 duplicated keys.
  - **Impact:** **High**
  - **Recommendation:** Replace with a typed `record`/struct per car and serialise only at the REST boundary. The duplicated "no car" and "car" branches should share one writer.

- [ ] **`SimEngine.Tick`** `DrivingGame.Sim/SimEngine.cs:648, 751, 844, 944`
  - **Type:** Hot-Path Allocation
  - **Finding:** Per frame: `carControl` dict (`:648`). Per substep, per collision branch: `prevPose` dict (`:751`), `impactSpeed` dict (`:844`), plus everything `ComputeAvoidCaps` allocates. Per frame: `_cars.Values.ToList()` (`:944`) just to iterate safely while resolving red flags.
  - **Impact:** **Medium**
  - **Recommendation:** Reuse per-car slots (store `prevPose` on `Car` as two doubles + a heading, no map). Hoist `impactSpeed` into the same per-car slot. Iterate `_cars.Values` with an explicit removal list instead of copying.

- [ ] **`CarCollisions.ComputeAvoidCaps`** `DrivingGame.Sim/CarCollisions.cs:425-1810`
  - **Type:** Hot-Path Allocation / Over-Complicated Logic
  - **Finding:** Called once per substep. Allocates at least twelve collections per call (`carList`, `caps`, `reasons`, `signedNodes`, `pConflicts`, `immediateConflict`, `routeAhead`, `routeOff`, `sweeps`, `r14Blocked`, `r14Blockers`, `r14Room`, `r14Node`, `lockCars`, …), plus a local closure `OfferCap` captured over `reasons`. The method is ~1385 lines with 6–8 levels of nesting and five interleaved rule families (v1 corridor, R8 yield, R26 passage, R14 entry gate, v2 TTC, sign rule) in one body.
  - **Impact:** **High**
  - **Recommendation:** Split into named passes (`CorridorCaps`, `CrossingConflicts`, `SignCaps`, `PassageClaims`, `EntryGate`, `Finalize`) over a reusable accumulator struct allocated once per engine. One rule per method makes the "which rule owns this cap" logic (`_v1Rule`, `_v1By`, `_v1Along`, `_v1Lat`, `_v1Gap`) readable instead of positional.

- [ ] **`CarCollisions.Grid.Near`** `DrivingGame.Sim/CarCollisions.cs:304-333, 446, 567, 742, 800, 822, 899, 2176`
  - **Type:** Hot-Path Allocation / Redundant Work
  - **Finding:** `Near(x, y, radius)` allocates a fresh `List<Car>` and probes `(2r+1)²` hash cells. With `ring = ceil(300/20)+1 = 16` (`:446`) that is **1089 hash lookups per car per substep** at `:567`; the pair ring at `:899` adds 361 more; `:742`/`:800`/`:822` add further rings. `Resolve` (`:2176`) uses radius 1 (9 lookups). The same grid is rebuilt twice per substep — once in `ComputeAvoidCaps`, once in `Resolve`.
  - **Impact:** **High**
  - **Recommendation:** Build the broadphase grid once per substep and pass it to both phases. Replace the square ring probe with a sorted-by-cell sweep or a radius-limited neighbour walk, and have `Near` write into a caller-owned buffer instead of allocating.

- [ ] **`CarCollisions.EarliestConflict`** `DrivingGame.Sim/CarCollisions.cs:1854-1893`
  - **Type:** Hot-Path Allocation
  - **Finding:** For every pair, every substep, it walks 50 sweep samples (`TtcSweepMaxS / TtcSweepStepS`) and allocates 4 objects per sample: two corner `List<(double,double)>` from `BoxCorners` and two `BodyBox` wrappers — ~200 allocations per pair per substep, before the SAT test.
  - **Impact:** **High**
  - **Recommendation:** Precompute each car's swept boxes once per substep (they are already swept per car in `sweeps`), store them in a flat array of four corners, and make `BoxesIntersect` take corner spans/`Span`s rather than boxed lists.

- [ ] **`Obstacles.ApplyContactStop`** `DrivingGame.Sim/Obstacles.cs:526-620`

  - **Type:** Polling pattern / manual callback plumbing
  - **Finding:** Two hand-built `HttpRequest` nodes (`_stateHttpA`/`_stateHttpB`) alternate as a double buffer, with `_busyA`/`_busyB` guards, a `_pollGen` counter to kill stale `GetTree().CreateTimer(0.1)` callbacks, and `_cmdHttpBusy`/`_clickPendingNum` for the command channel.   - **Impact:** **Medium**
  - **Recommendation:** In embedded mode this whole branch is dead — make it one code path. For the HTTP mode, one `HttpRequest` node plus a single "request finished → request again" signal is enough; the alternating pair exists only to hide latency, which a 60 Hz sim feed does not need.

- [ ] **Static/global mutable state keyed by uid** `CarCollisions.cs:287, 291, 292, 293, 362, 371, 372, 1898, 1899, 1900` · `LaneGuard.cs:51, 100-121` · `PhysicsValidator.cs:36, 38` · `CrashDumper.cs:26` · `SimEngine.cs:142` · `Raceline.cs:787, 788`

  - **Impact:** **High** (correctness + memory)
  - **Recommendation:** Move per-car state onto `Car` (it already carries `ActiveCapKey`, `AlertOtherUid`, `YieldRightM`, …) or into a `SimEngine`-owned struct with one clear-on-remove path. Make `Dumped` a set of `Car.Uid`. Bound `StandstillErrors` the way `Car.Decisions` is bounded.

  - **Finding:** The entire collision system is static functions over static mutable fields, so two `SimEngine`s share it. `Program.cs --bench` creates a fresh engine per phase (`:230`) and the collision state silently carries across phases; the embedded and console hosts would collide with each other in one process.

- [ ] **`SimEngine.SetControl` / `GetControlFor` / `ClearControl`** `DrivingGame.Sim/SimEngine.cs:152, 583, 596-640`
  - **Type:** Pythonic paradigm — untyped dict where a typed object belongs

  - **Type:** Pythonic paradigm (`dict.update`) / correctness hazard
  - **Finding:** The payload is a persistent dictionary merged per key — "Merge per key (Python: `game_state.update(state)`) - keys set by an earlier variant survive".   - **Impact:** **Medium**
  - **Recommendation:** Emit a complete, explicit payload each tick (no merge). If the REST contract must keep every key present in the no-car shape, say so in the payload rather than inheriting stale values.

- [ ] **`SimEngine.Tick` structure** `DrivingGame.Sim/SimEngine.cs:690-960`

- [ ] **`PhysicsValidator` violation messages** `DrivingGame.Sim/PhysicsValidator.cs:97-112, 143-151, 190-198`
  - **Type:** Un-idiomatic C# / Python idiom
  - **Finding:** The exception argument is built eagerly with the Python `'=' * 70` banner idiom inside the `throw`, and `PhysicsViolationException` has **no catch site anywhere in the runtime** (only `Assert.Throws` in `SafetySystemsTests.cs:345, 377`). - [ ] **`Raceline.MinCurvatureOffsets`** `DrivingGame.Sim/Raceline.cs:144-260`

**What the numbers change in §2:**

- **H6 (`LaneGuard.SignedRightOffset`) is the single biggest cost, not `avoid`.**
  405 µs/car/step, 57 % of the step, and it is **flat in car count** (406.8 → 404.6
  from 50 → 100 cars) — exactly the signature of an O(map vertices) scan that does
  not depend on traffic. It is the reason the sim stops holding real time, and
  fixing it alone would take the total from ~705 to ~300 µs/car/step.
- **H8/H9 (`avoid`) is second, and it is the part that scales with cars**
  (114 → 184 µs, +61 % for +50 cars). It is what bounds the capacity ceiling once
  `guard` is fixed.
- **H7 (`ApplyContactStop`) is NOT a current bottleneck** — 0.07–0.09 µs/car/step,
  because the test map has no obstacles. Its cost is conditional on obstacle
  count; the finding stays valid as a latent cost, but its Impact drops to
  **Low on an empty map / High only with obstacles**.
- **`resolve` is cheap** (1.5–2.4 µs) — the pair loop in `Resolve` is not where
  the time goes; `ComputeAvoidCaps`'s sweeps are. H9 stays, H8's "share the grid"
  half matters more than its "precompute boxes" half.
- **`validate` (47–64 µs) confirms H5**: `PhysicsValidator.CheckOffRoad` →
  `IsCarOnRoad` is a real cost, second tier.
- **`payload` (49–67 µs/frame) confirms H3/H4** are worth doing, but they are
  ~7 %, not the top of the list.
- **`update` fell 86.8 → 18.3** between the two windows: the first window pays
  the cold `Raceline` solve cache. That is warm-up, not steady state — the
  `Raceline.cs:780-790` comment ("after warm-up every rebuild is a cache hit")
  is borne out by the measurement.

**Budget verdict:** measured 705–741 µs/car/step against the spec's ~200 —
**3.5–3.7× over budget**, and the over-run is one function.

**Caveats, stated honestly:**
- This is the `basic` test map's `fig8_n` loop, single-threaded, one core.
- The `basic` map has no obstacles, so `contact` measures the empty-map path.
- `payload*` is per frame, not per substep — at `--warp N` its per-substep share
  is N× lower than printed.
- The 21 `// TEMPORARY` debug blocks (H11) were **active during this run**
  (`DBGV1`, `DBGV2`, `DBGCAP`, `[TBLINK]` lines filled the log). They are inside
  the measured stages, so the stage figures include that logging. Removing them
  first (H11) and re-measuring is the honest next step — the ranking will not
  change, the absolute numbers should get smaller.

## 5. Follow-up: the 23 failing unit tests, and the lane-guard fix (2026-10-20)

**The 23 failures were a stale fixture, not a regression.** Isolated with a
temporary worktree: HEAD (`a6fbaa2`) runs **91 passed / 2 skipped / 0 failed**;
copying `DrivingGame.Sim/TestMaps.cs` from the working tree alone reproduces all
23. No other modified file contributes a single failure.

Cause: `data/raceline_reference/basic.json` records the **`basic` map** (183
nodes / 166 segments, `sweep_*` and `www_*` tiles present, no `straight_m`).
The in-progress `TestMaps.cs` edit split the straight road at a new `straight_m`
node and deleted the sweeping-curve and WWW tiles (269 nodes / 256 segments now).
The recorded routes name nodes and segment indices that no longer exist.

**Fixed by re-baselining**, and the re-baseline tool needed three corrections
before it could do it (it had never been run — it is `Fact(Skip=…)`):

1. it kept the **old** case inputs (`c.Rounded`, `c.SegIdx`) and only re-solved
   them — correct for a raceline change, wrong for a map change. Now it
   re-resolves each recorded route **by node name** on the current network, and
   re-derives `rounded` from the current node positions.
2. a split road was still unresolvable, so `straight` would have been dropped.
   `HopOf` now allows one intermediate node (what a deliberate road split
   creates); `straight` re-resolves to `straight_n → straight_m → straight_s`.
   It walks `net.Segments` for adjacency — `NodeConnections` is only populated
   by the OSM loader, so it is empty for test maps.
3. two write-side bugs, both found by the failures they caused:
   - normals were written through the frame-scaled `PtsJson` (length 2 =
     `pxPerM`) while the loader reads them unscaled → every case failed at
     `N[0]`.
   - `props` and `junction` were copied from the **old** case instead of the
     recomputed ones → `IndexOutOfRange` and wrong `StationProps`.

**Result: 91 passed / 2 skipped / 0 failed** — the documented baseline, with all
23 reference cases kept and the `Skip` annotation restored (the tool must stay
skipped, or the reference tests become self-fulfilling).

**The lane-guard fix (H6) landed in the same session:**

- new `DrivingGame.Sim/LaneGeometry.cs` — declared lane structure per segment
  (`Width` / `Lanes` / `ParkingLaneWidth` / `Oneway` → lateral offsets), cached
  on the network via `RoadNetwork.LaneGeometryCache`.
- `LaneGuard` now queries `SmoothedNetwork.SegmentCurve[(SegIdx, Forward)]` — a
  window of samples around the car's own arc position, widened once only when
  the car is genuinely far off the line. Cost is bounded by the **segment**, not
  the map. The whole-map `MultiLineString` cache and the double measurement are
  gone; "no centreline here" is now an explicit `Known = false` instead of
  reading as "exactly on the line".

| | before | after |
|---|---|---|
| `guard` | 405 µs/car/step | **8.6 µs** |
| step total | ~705 µs/car/step | **~316 µs/car/step** |
| capacity | never measured (50 and 100 both failed) | **66 cars** (binary search: 66 → pace 0.981, 68 → 0.906) |

**Still open:** lane-bound **enforcement** (stay inside your lane unless the
move is intentional) is not wired — `LaneStrip` carries the offsets and says so
in its comment, but the guard still asks only the centreline question. And the
e2e gate (`scripts/run_e2e.sh --warp 4`, expected 21/23) has not been run since
this change.
